===============================================================
  "MY REPOSITORIES ARE PUBLIC — HOW DO I MAKE THEM PRIVATE?"
  16 September 2026
===============================================================

  SHORT ANSWER

  Do not make them private. If you do, all three of your
  sites go offline immediately.

  You are on the free GitHub plan. Free GitHub Pages only
  serves from PUBLIC repositories. The moment a repo goes
  private, Pages is switched off and hsbfix.org,
  app.hsbfix.org and admin.hsbfix.org start returning 404.

  Worse: switching back to public does NOT automatically
  turn Pages back on. You have to re-enable it by hand,
  re-add the custom domain, and check the CNAME file
  survived. People lose hours to this.

  There are two real jobs here and they get confused with
  each other:

    1. Are my SECRETS exposed?        <- this is what matters
    2. Is my SOURCE CODE visible?     <- this barely matters

  I checked number 1 today. You are clean.

===============================================================
  WHY A PUBLIC KEY IN config.js IS NOT A LEAK
===============================================================

  It is worth understanding this properly, because it is the
  thing that makes the whole free-hosting setup safe.

  The key in config.js is called the PUBLISHABLE key. It is
  designed to be public. It identifies your project; it does
  not grant access to anything. Every Supabase app in the
  world ships it in the browser, because the browser has to
  have it to connect at all.

  What stops a stranger reading your customers' data is Row
  Level Security — rules inside the database that check who
  is asking before returning a single row. I tested those
  above. They hold.

  The key that WOULD be a disaster is the SERVICE ROLE key,
  which bypasses RLS entirely. That one lives only in
  Supabase's secret store, and I confirmed it is not in any
  file. Never put it in config.js, never put it in any
  front-end file, never paste it into a repo.

  Rule of thumb: sb_publishable_... is fine in public.
  sb_secret_... or service_role is never fine anywhere
  except Supabase Edge Function secrets.

===============================================================
  IF YOU STILL WANT THE CODE PRIVATE
===============================================================

  Understandable — it is your work, and you are selling it.
  There are three honest options.

  OPTION 1 — LEAVE IT. Free. Recommended for now.

    Your competitors cannot use your code without your
    database, and your database is locked. Anyone can
    already read your front-end code anyway, whatever you
    do: browsers download JavaScript to run it, so
    "View Source" on app.hsbfix.org shows it regardless of
    whether the repo is public. Making the repo private
    hides the commit history, not the running code.

    This is the part most people miss. For a static site,
    private repo buys you very little.

  OPTION 2 — CLOUDFLARE PAGES. Free, and it does work.

    Cloudflare Pages will serve a site from a PRIVATE GitHub
    repo on its free plan. Same deal as GitHub Pages: you
    push to the repo, it deploys. Custom domains included.

    Cost: nothing. Effort: about an hour to move three
    sites and re-point DNS, plus the risk of downtime while
    domains propagate.

    Do this when you have a calm afternoon. Not today, and
    not while something else is broken.

  OPTION 3 — GITHUB PRO. Paid.

    Lets private repos publish to Pages. You told me you did
    not want more monthly costs, so I am listing it only for
    completeness. It also does NOT make the published site
    private — the site stays public either way. You would be
    paying purely to hide the source, which Option 2 does
    for free.

  MY ADVICE: Option 1 now, delete the two stray files today,
  and consider Option 2 later if it still bothers you.


===============================================================
  WHAT TO DO IF A REAL KEY EVER LEAKS
===============================================================

  Worth knowing before it happens. If a service role key,
  Resend key or Gemini key ever ends up in a public repo:

  Deleting the file is NOT enough. Git keeps history, and
  bots scrape public repos within minutes of a push.

  You must ROTATE the key — generate a new one and revoke
  the old:

    Supabase service role  Settings > API > roll the key,
                           then update the Edge Function
                           secret
    Resend                 API Keys > revoke > create new,
                           update Supabase SMTP password
    Gemini                 Google AI Studio > delete key >
                           create new > update the
                           GEMINI_API_KEY secret

  Assume any key that touched a public repo is burned.
  Rotating takes ten minutes. Cleaning up after a stolen
  service role key takes days.
