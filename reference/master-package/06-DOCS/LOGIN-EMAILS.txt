===============================================================
  PROBLEM A — "SENT" BUT NEVER DELIVERED
===============================================================

  THE CAUSE

  Your project is still using Supabase's built-in mailer.
  It has two hard limits that explain exactly what you saw:

    1. It only delivers to PRE-AUTHORISED ADDRESSES — in
       practice, the email address on your own Supabase
       account. Anyone else gets nothing.

    2. It sends only 2 EMAILS PER HOUR for the entire
       project, shared across signups, invites and resets.

  Neither failure shows an error. The app calls the function,
  Supabase accepts it, your panel honestly reports "sent",
  and the email is silently dropped. That is why it looked
  like the panel was lying.

  Paying for Pro does NOT change this. The limit belongs to
  the built-in mailer, not the plan.


  THE FIX — CONNECT A REAL MAIL SENDER (free)

  I suggest Resend: free tier is 100 emails a day, which is
  far more than you need, and it is the quickest to set up.

  Step 1 — make the account
    Go to resend.com and sign up.
    Add your domain hsbfix.org.
    It will give you 3 DNS records (SPF, DKIM, DMARC).
    Add those wherever you manage hsbfix.org DNS.
    Wait for it to show "Verified" — usually minutes.

    Skipping domain verification is possible for testing,
    but then your mail lands in spam. Do the DNS records.

  Step 2 — create an API key
    In Resend: API Keys > Create. Copy it. It starts "re_".

  Step 3 — put it into Supabase
    Supabase dashboard
      > Authentication
      > Emails  (SMTP Settings)
      > turn ON "Enable Custom SMTP"

    Host        smtp.resend.com
    Port        465
    Username    resend
    Password    <your re_... API key>
    Sender      no-reply@hsbfix.org
    Sender name PlantMaster Pro

    Save.

  Step 4 — raise the limit
    Supabase > Authentication > Rate Limits
    Custom SMTP starts at 30 emails/hour. Raise it to
    something sensible like 100.

  After this, resets reach ANY customer, not just you.


===============================================================
  PROBLEM B — LINK OPENS hsbfix.org
===============================================================

  THE CAUSE

  Supabase will only redirect to addresses on its allow list.
  Anything not on the list falls back to the project's
  Site URL — which is set to your marketing site, hsbfix.org.
  So the link "worked", logged the user in, and dumped them
  on the wrong website.

  THE FIX

  Supabase dashboard
    > Authentication
    > URL Configuration

  Set Site URL to:

      https://app.hsbfix.org

  That is where most users go, so it is the right fallback.

  Then add ALL of these under Redirect URLs:

      https://app.hsbfix.org
      https://app.hsbfix.org/**
      https://app.hsbfix.org/index.html
      https://admin.hsbfix.org
      https://admin.hsbfix.org/**
      https://admin.hsbfix.org/index.html

  Save.

  The /** entries matter — without them Supabase rejects any
  link carrying a token or query string, which is every
  reset link.


===============================================================
  WHAT I FIXED IN THE CODE
===============================================================

  These are real bugs I found while checking, and they would
  have bitten you even after the dashboard work.

  1. CUSTOMER APP — reset links using the hash format were
     ignored.

     The app only looked for "?type=recovery" or "?code=" in
     the query string. Supabase also issues links in the form

         #access_token=...&type=recovery

     which is in the HASH, not the query. Those links logged
     the user straight into the dashboard instead of showing
     the new-password screen. It now checks both, and also
     listens for Supabase's PASSWORD_RECOVERY event, which is
     the most reliable signal of all.

  2. ADMIN PANEL — reset only worked in the same browser.

     It set a flag in sessionStorage when you pressed Forgot
     password, then looked for that flag when the link opened.
     On a phone, the email usually opens in a DIFFERENT
     browser, where that flag does not exist — so the panel
     ignored the reset and showed the login screen. It now
     reads the URL as well, in all three formats.

  3. ADMIN PANEL — redirect targets made explicit.
     Your own reset returns to the admin panel; a reset you
     send to a customer goes to the customer app's index.html
     rather than a bare domain.

  4. The "check your email" message now warns that delivery
     may be blocked by the built-in mailer, so a future you
     is not misled again.
